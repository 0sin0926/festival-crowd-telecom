# 프롬프트 로그 — 인원수 시계열 예측 모델링 과정

## 프롬프트 개선 과정 (v1 → v4, 3회 개선)

같은 질문인 "평소 인원 예측 모델을 어떻게 설계할 것인가"를 네 번 고쳐 물으면서 답변이 어떻게 달라지는지 기록했습니다. v1은 10/9 실제 대화이고, v2~v4는 10/15에 개선한 프롬프트로 다시 실행한 결과입니다.

| 버전 | 바꾼 것 | 노린 효과 |
|---|---|---|
| v1 | (원문) 질문만 던짐 | — |
| v2 | 역할, 데이터, 목적, 출력 형식 지정 | 목적에 맞는 학습 범위가 처음부터 나오게 함 |
| v3 | 검증 방법, 비교 모델, 분량, 불확실성 표시 조건 추가 | 모델 선택의 근거와 검증 설계를 받음 |
| v4 | 직무 관점 변경 (통신 → 안전관리) 후 비교 | 같은 결과를 관점별로 다르게 해석하는지 확인 |

### v1 — 원문 (2026-10-09)

**(사용자)**
그래서 평소 인원수는 회귀예측인지 뭔지 뭘하겠다는거야

**(Claude, 요약)**
회귀 예측입니다. 입력은 구역·요일·시각·월·공휴일·기온·강수, 출력은 그 구역 그 시각의 인원이고, 모델은 LightGBM 같은 트리 기반 회귀입니다. 축제일 조건을 넣어 "축제가 없었다면 있었을 인원"을 구하는 데 씁니다.

**문제점**
- 역할과 목적이 없어서 앞선 답변에 따라 구조가 계속 바뀌었습니다. 같은 대화에서 Claude 스스로 "여러 번 구조를 바꿔 말해서 혼란을 드렸다"고 했습니다.
- 학습 범위가 정해지지 않아 전 요일 학습을 전제로 답했습니다. 주말만 쓰자는 결론은 질문을 두 번 더 한 뒤에야 나왔습니다.
- 검증 방법과 비교 대상이 없어서 "왜 그 모델인가"에 답할 근거가 없었습니다.

### v2 — 역할·데이터·목적·출력 형식 지정 (2026-10-15)

**(사용자)**
당신은 통신사 네트워크 운영팀의 데이터 분석가입니다.
- 데이터: 여의도 5개 구역의 시간별 생활인구(2023.01~2026.07, 통신 신호 기반 추계), 같은 기간 시간별 날씨(기온·강수·습도 등), 여의도 행사 달력
- 목적: 불꽃축제 당일 "축제가 없었다면 있었을 평소 인원"을 구해, 실제 인원과의 차이(증가분)를 계산하는 기준선으로 씁니다.

이 목적에 맞는 평소 인원 예측 모델을 설계해 주세요. 문제 유형, 입력 변수, 출력, 학습에 쓸 날짜 범위를 표로 제시하세요.

**(Claude)**

| 항목 | 설계 |
|---|---|
| 문제 유형 | 회귀 (인원은 연속값) |
| 단위 | 구역별로 모델 1개씩, 1시간 단위 |
| 입력 변수 | 시각, 요일 유형(토 / 일·공휴일), 월, 연휴 여부, 기온, 체감온도, 강수량, 습도 |
| 출력 | 그 구역, 그 시각의 인원 (학습할 때는 로그 변환) |
| 학습 날짜 | 행사가 없는 토·일·공휴일만 |
| 추천 모델 | 그래디언트 부스팅 회귀 |

- **평일을 빼는 이유**: 불꽃축제는 토요일에 열립니다. 여의도는 평일 낮에 직장인이 몰려 평일과 주말의 패턴이 완전히 다르고, 평일을 섞으면 표본의 약 70%인 평일을 맞히는 쪽으로 학습됩니다.
- **행사일을 빼는 이유**: 목적이 "축제가 없었다면"이므로, 다른 행사로 사람이 몰린 날이 섞이면 기준선이 높아지고 증가분이 작게 계산됩니다.
- **로그 변환**: 구역마다 인원 규모가 수천~수만 명으로 달라, 큰 값에 오차가 끌려가지 않게 합니다.

**개선된 점과 남은 문제**
목적을 알려 주니 "주말만, 행사일 제외"가 첫 답변부터 나왔습니다. v1에서는 질문을 세 번 더 해야 얻은 결론입니다. 그러나 그래디언트 부스팅을 고른 근거와 성능을 어떻게 검증할지는 여전히 없습니다.

### v3 — 검증·비교·형식 조건 추가 (2026-10-15)

**(사용자)**
(v2 프롬프트에 이어서)

[조건]
1. 시계열 데이터이므로 미래 정보가 학습에 섞이지 않는 검증 방법을 제시할 것
2. 단순 평균 방식을 포함해 비교 모델을 3개 이상 제시하고, 비교 지표를 정할 것
3. 추천 모델을 고른 이유와 예상되는 한계를 각각 3줄 이내로 쓸 것
4. 확실하지 않은 내용은 "확인 필요"로 표시할 것

**(Claude)**

**검증 방법: 시간 순서 교차검증**
무작위로 섞어 나누면 같은 토요일의 14시가 학습에, 15시가 시험에 들어가 답을 본 채로 시험을 치게 됩니다. 앞 기간으로 학습하고 뒤 6개월로 시험하는 구간을 4개 만들어 평균을 냅니다.

| 구간 | 학습 | 시험 |
|---|---|---|
| 1 | 2023.01~2024.06 | 2024.07~12 |
| 2 | 2023.01~2024.12 | 2025.01~06 |
| 3 | 2023.01~2025.06 | 2025.07~12 |
| 4 | 2023.01~2025.12 | 2026.01~07 |

하이퍼파라미터는 시험 기간이 아니라 학습 기간의 마지막 20%로 고릅니다.

**비교 모델과 지표**

| 모델 | 비교하는 이유 |
|---|---|
| 요일 유형 × 시각 평균 | 모델 없이도 이 정도는 나온다는 최소 기준 |
| 월 × 요일 유형 × 시각 평균 | 계절을 반영한 단순 기준 |
| 선형회귀 (Ridge) | 변수 간 상호작용이 없는 모델 |
| 랜덤포레스트 | 트리 기반 앙상블 |
| 그래디언트 부스팅 | 추천 모델 |

지표는 구역별 오차율(절대 오차의 합 ÷ 실제 인원의 합)과 평균 오차(명)를 씁니다. 구역마다 인원 규모가 달라서 비율 지표가 있어야 구역끼리 비교할 수 있습니다.

**추천 이유**
- 시각 × 기온 × 요일처럼 변수끼리 얽힌 효과(더운 날 낮에만 줄어드는 식)를 따로 지정하지 않아도 잡습니다.
- 표 형태 데이터에서 성능이 좋고, 이 규모(수백 일 × 24시간)에서는 학습이 몇 초면 끝납니다.
- 변수 중요도를 볼 수 있어 결과를 설명하기 쉽습니다.

**예상 한계**
- 행사 달력에 없는 집회 같은 날이 "평소"로 섞일 수 있습니다. (확인 필요: 오차가 튀는 날을 따로 살펴봐야 함)
- 강변 구역은 날씨에 따라 변동이 커서 업무지구보다 오차율이 높을 것입니다.
- 데이터가 2026년 7월에 끝나서 그 이후 날짜는 실제 값과 맞춰 볼 수 없습니다.

**개선된 점**
비교 모델과 검증 설계까지 받았고, 이 구조가 10/11에 실제로 수행한 모델 비교(7장)와 같습니다. 실행 결과 그래디언트 부스팅이 6구역 평균 오차율 14.2%로 가장 좋았습니다. "집회일이 섞일 수 있다"는 한계도 실제로 일어났습니다(2024년 12월 탄핵 집회).

### v4 — 직무 관점 바꾸기 (2026-10-15)

**(사용자)**
아래는 우리 모델로 2026년 9월 5일 서울세계불꽃축제를 예측한 결과입니다.
- 여의동 전체 19시 피크: 362,495명 (맑은 날 시나리오)
- 공원 동쪽 19시 피크: 약 9만 명
- 오전 비 후 갬 시나리오: 축제 증가분이 15시에 맑은 날의 0.45배, 19시에 0.92배

당신은 영등포구청 재난안전 담당자입니다. 이 결과를 보고 내릴 판단을 정리하고, 같은 결과를 통신사 네트워크 운영 담당자가 볼 때와 어떻게 다른지 표로 비교해 주세요.

**(Claude)**

| 관점 | 통신사 네트워크 운영 담당자 | 구청 재난안전 담당자 |
|---|---|---|
| 주로 보는 값 | 증가분 (기존 기지국이 평소 인원을 감당한다고 보고) | 전체 인원 (평소 + 증가분) |
| 핵심 숫자 | 구역별 피크 증가분 → 이동기지국 대수 | 공원 동쪽 약 9만 명 → 면적당 밀집도 |
| 중요한 시각 | 유입이 시작되는 시각 → 장비 가동 시작 | 피크 직후 21시 무렵 → 한꺼번에 빠져나가는 귀가 인파 |
| 오전 비 후 갬일 때 | 15시 인원이 절반 이하라 가동 시작을 늦춰도 됨 | 늦게 온 인파가 짧은 시간에 몰려 오히려 입장 통제가 더 급해짐 |
| 구역별 우선순위 | 증가분이 큰 공원 동쪽 > 진입부 | 출구가 좁은 진입부와 역 주변 동선이 먼저 |

- 통신 관점에서 "비 오면 오후 수요가 줄어드니 여유가 생긴다"는 결과가, 안전 관점에서는 "몰리는 시간이 짧아져 더 위험하다"로 바뀝니다. 같은 0.45배를 반대로 읽게 됩니다.
- 안전관리 쪽에서 주의할 점: 생활인구는 내국인만 포함하므로 실제 현장 인원은 이보다 많습니다. 밀집도 판단에는 여유를 두고 써야 합니다.

**개선된 점**
관점만 바꿔도 같은 숫자에서 우선순위가 다르게 나왔습니다. 특히 오전 비 시나리오는 통신 쪽에서는 부담이 줄어드는 정보, 안전 쪽에서는 위험이 커지는 정보로 해석이 갈렸습니다.

## 1장. 모델 구조 잡기 — "모델은 어디에 쓰는가" (10/9)

**(사용자)**
지금까지의 논의를 정리해서 확인하고 싶습니다. 실제로 모델이 쓰이는 분석은 수백 일에 걸친 평소 인원 데이터 분석이고, 그 결론은 "보편적인 하루의 인원수 시계열"이 되는 건가요? 다르다면 어떤 점이 다른지 설명해 주세요.

**(Claude)**
거의 맞는데 두 가지를 바로잡아야 합니다. 모델이 다루는 건 "증가분"이 아니라 **평소 인원 그 자체**이고, 그 결과는 프로젝트의 결론이 아니라 **결론을 내기 위한 기준선**입니다.

| | 평소 인원 | 축제 증가분 |
|---|---|---|
| 데이터 | 축제 없는 날 수백~수천 일 | 불꽃축제 7회 |
| 방법 | 모델 학습 가능 | 분해와 평균 |
| 프로젝트에서의 위치 | 기준선 | **결론** |

(중략) 핵심 질문에 모델을 쓰려면 서울 전체의 여러 행사를 모아 증가분을 예측하는 모델로 확장하는 방법이 있습니다.

**(사용자)**
전제를 다시 짚겠습니다. 분석 단위는 여의도 전체가 아니라 **여의도 내 구역별** 시간대별 인원입니다. 그래서 서울 전체 행사로 확장하는 안은 범위에서 제외합니다. 이 전제 안에서 모델 구조를 다시 제안해 주세요.

**(Claude)**
맞습니다. 서울 전체로 넓히는 안은 접겠습니다. 목표는 **여의도 구역별·시간대별 인원**이고, 그 범위 안에서 모델을 쓸 자리가 충분히 있습니다.
(중략) 모델은 하나로 잡습니다. "여의도의 이 구역, 이 날, 이 시각에 몇 명인가"를 예측하는 모델입니다. 입력은 시간 조건, 날씨, 구역 속성, 행사 정보, 직전 흐름입니다.

**(사용자)**
두 가지를 확인하고 싶습니다.
1. 불꽃축제에는 명당자리가 있습니다. 이 때문에 당일 구역 간 이동 패턴이 평소와 달라지지 않을까요?
2. 평소 인원 예측은 어떤 문제 유형(회귀, 분류 등)으로 정의하고, 입력과 출력은 무엇으로 두나요?

**(Claude)**
**1.** 네, 달라집니다. 축제일에 불꽃 정면인 공원 동쪽은 평소의 17.7배였고, 서쪽 강변은 2.9배였습니다. 사람들이 "역에서 가까운 곳"이 아니라 "불꽃이 잘 보이는 곳"으로 가기 때문에, 평소 날에서 배운 이동 규칙은 불꽃축제 날에 통하지 않습니다.

**2.** **회귀 예측**입니다.
- 입력: 구역, 요일, 시각, 월, 공휴일 여부, 기온, 강수
- 출력: 그 구역, 그 시각의 인원
- 모델: 트리 기반 회귀 (예: LightGBM)

쓰임새는 축제일의 조건을 넣어 **"축제가 없었다면 이 구역에 몇 명이 있었을지"**를 구하는 것입니다. 실제 값에서 이걸 빼야 축제로 늘어난 인원이 나옵니다.

| 부분 | 방법 | 표본 |
|---|---|---|
| 평소 인원 | 회귀 모델 | 수천 일 |
| 불꽃축제 증가분 | 7회의 분해와 평균 | 7회 |
| 예측 | 평소 인원 + 증가분 | — |

(중략)

**(사용자)**
증가분의 정의에 관한 질문입니다. 평소 그 시간에 여의도에 있었을 사람 중 일부는 불꽃축제 혼잡을 피해 오지 않았을 것입니다. 이 효과는 계산에 어떻게 반영되나요?

**(Claude)**
네, 그럴 겁니다. 다만 이건 계산을 틀리게 만드는 게 아니라 **증가분을 뭐라고 부를지**를 바꿉니다. 실제 − 평소는 "축제 관람객 수"가 아니라 **"평소 대비 순증가"**입니다.

## 8장. 남은 의문 — 평균과 온도

**(사용자)**
예측에 과거 회차 증가분의 평균을 쓰는 이유를 다시 설명해 주세요.

| 맞히려는 해 | 직전 해 값 그대로 | 그때까지의 평균 |
|---|---|---|
| 2023 | +1.6% | +1.6% |
| 2024 | −15.2% | −14.5% |
| 2025 | +6.4% | −3.9% |

증가분을 모델로 학습시키기엔 표본이 4회뿐이고, 추세를 그리면 2024년 하나에 크게 좌우됩니다. 표본이 이렇게 적을 때는 단순 평균이 가장 덜 위험한 선택입니다.

**(사용자)**
축제 당일 기온은 해마다 다릅니다. 증가분 평균에 이 차이가 반영되지 않아도 괜찮은지 검토해 주세요.

| 연도 | 19시 기온 | 피크 증가분 |
